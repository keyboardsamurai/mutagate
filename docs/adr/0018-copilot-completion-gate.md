# ADR-0018: Copilot completion gate
Status: accepted 2026-11-09
Concern: A Copilot `agentStop` hook has a timeout (`timeoutSec`, default 30 s). At the timeout, Copilot sends SIGTERM to the process group of the hook, sends SIGKILL 2 s later and then allows. This kill does not reach the runner process groups. Copilot reads only `decision` and `reason` from the `agentStop` output. `{"type":"progress",…}` lines are for display only, and with `-p` they show nowhere. After 8 blocks in a row, Copilot ends the turn. A `-p` session can end with no more tool calls. The bash tool puts a command in the background after `initial_wait` (default 30 s). Evidence: Copilot CLI 1.0.107, spikes S2, S5, S6, S7, S8 and S13 (#35).
Decision: The `agentStop` hook command is `hook Stop --harness copilot --timeout T`, with `timeoutSec` T. Without `--timeout`, T is 30 s. The margin M is min(30, ⌊T/4⌋) s. The gate deadline G is min(`gateBudgetSec`, T − 2M). For T = 600, G is 120 s. The gate waits for a run in flight for min(`gateWaitSec`, G) or less. It starts an inline run or the ADR-0003 retry only when `gateAdvice` says the run fits before G (ADR-0005). When a target stays pending and no run is in flight, the gate also starts a worker (`schedule`). The pending text that names `check --wait N` also tells the agent to set bash `initial_wait` to N + 30 or more. At W = T − M, a watchdog allows with a progress line, writes the trace decision `deadline` and stops the process. The exit handler of `runners.cjs` then kills the runner process groups. The session state keeps `stopStreak`. An `agentStop` with `stop_hook_active` false sets it to 0. A block sets it to its value before this `agentStop` plus 1. When `stopStreak` is 8, the gate does not use a block round (`claimBlock`) and allows with the progress line `Copilot block limit`. `stop_hook_active` alone does not cause an allow. The hook always exits 0. A block is exactly one `{"decision":"block","reason":…}` object. An allow is empty stdout or one progress line: the round cap, a warning, the advise-mode report or a diagnostic. mutagate does not write stderr, plain text, `systemMessage` or `modifiedResponse`. The trace decision is `block` for a block or exit 2, and the trace row has `exit`. The `agentStop` of a subagent (payload `agentId`) exits 0 with no decision; the root `agentStop` gates the writes of the subagent (ADR-0020). A second delivery of one `agentStop` (a duplicate hook file) is a second gate pass.
Rationale: G and W keep ADR-0003, ADR-0004 and ADR-0005 inside the Copilot timeout. Spike S5 showed a 120 s hook under `timeoutSec` 600. M gives the hook time to write its output before the kill. A worker continues after the `-p` session ends (S6). Without `initial_wait`, `check --wait N` goes to the background after 30 s. Copilot ignores a ninth block in a row, so a block round used there is lost. Plain text or two JSON objects make Copilot ignore the block. `modifiedResponse` can undo the redaction of another hook.
Alternatives: A short `timeoutSec` and a marker that a later `agentStop` reads (#35 D6b). Not built: if VS Code limits the timeout or its UI is not usable, mutagate does not claim VS Code. The default 30 s timeout. G becomes 16 s, too short for most runs. Rejected. Exit 2 for a block. Copilot documents exit 2 as a warning. Rejected.
Consequences: An `agentStop` can hold the session for up to W (570 s for T = 600), and `-p` and text mode show no output during the wait. The model does not see allow-time messages. The user sees them only in the interactive CLI, and the trace keeps the decision. A blocking `agentStop` hook of another tool that runs after mutagate replaces the mutagate reason and uses its block. `stopStreak` counts only mutagate blocks.
