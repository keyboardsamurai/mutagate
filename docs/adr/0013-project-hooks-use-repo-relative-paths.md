# ADR-0013: Project hooks use repo-relative paths
Status: accepted 2026-09-16
Concern: A project install wrote the absolute Node path and the absolute runtime path into `.claude/settings.json` and `.codex/hooks.json`. It wrote the same paths into the OpenCode and Pi adapters. Teams commit these files. On another machine or in CI, the hooks fail.
Decision: A project install is a portable install when the skill `scripts/` dir is inside the Git top level. For Claude and Codex, each command is then `f="$(git rev-parse --show-toplevel)/<rel>/hook" && [ -f "$f" ] && sh "$f" <Event>`. The `[ -f ]` test is necessary: dash exits 2 when it cannot open the script, and exit 2 is a block. The adapters get the runtime path relative to the adapter file. The install writes the old absolute form when the repo has no Git or the skill is outside the Git top level. It also writes the absolute form when the relative path has characters other than `[\w./-]`, or on Windows. Such an install is machine-local, and the install output says so. User scope always writes the absolute form, without that warning.
Rationale: The Git top level does not change when the session starts in a subdirectory. In Claude Code 2.1.273 (pin 2.1.270), `CLAUDE_PROJECT_DIR` names the directory where the session started, not the Git top level. Claude Code 2.1.273 ran the command from the root. With `--settings`, it also ran the command from a subdirectory, in a repo path with a space. Without `--settings`, Claude started in a subdirectory did not load the root settings. Codex 0.154.0 loaded the root `.codex/hooks.json` from the root and from a subdirectory. It ran the command in both cases. The explicit `sh` does not need the exec bit.
Alternatives: `$CLAUDE_PROJECT_DIR` as the base path for Claude; it names the start directory, not the Git top level. Absolute paths only; committed config fails on other machines. Both rejected.
Consequences: Codex users trust the hooks again in `/hooks` after the command changes. Teammates need the skill dir: commit it. Without the skill dir, each hook event exits 1. The harness reports the failed hook and does not block. The hook also fails without blocking: without `git`, with a working directory outside the installing worktree, or in a submodule or nested repo. The hook needs `git` on PATH. `scripts/.node-path` is machine-local, and `scripts/.gitignore` keeps it untracked. Hooks under Node older than 22 stay inactive, and SessionStart says so.
Related: ADR-0011 (the live records that validate this install form follow its two-runs rule)
