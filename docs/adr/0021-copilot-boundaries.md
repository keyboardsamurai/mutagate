# ADR-0021: Copilot support boundaries
Status: accepted 2026-11-09
Concern: The native Copilot hook file (`.github/hooks/mutagate.json`) also reaches callers that mutagate does not support. The VS Code Local agent harness reads `.github/hooks` and sends Local payloads that have `hook_event_name` and block on exit 2. The committed file reaches each job of the Copilot cloud coding agent, which runs the hooks of `.github/hooks`, `.github/copilot/settings.json` and `.claude/settings.json` (spike S16). The Copilot sandbox can make the cache root read-only, so state, locks and workers fail. Copilot runs each hook file that it finds, in the project and the user scope. It runs `command` also under PowerShell when an entry has no `powershell` field. It denies the tool call when a `preToolUse` hook fails. When two `agentStop` hooks block, only the reason of the last one gets to the model. Copilot also reads skills from `.claude/skills`. The VS Code docs do not accept results from CLI runs as evidence for VS Code.
Decision: A `--harness copilot` hook call whose payload has `hook_event_name` is a VS Code Local call. It exits 0 and does nothing else: no state, trace, recording or stdout. The spawned `--mutate` handler is not a Local call. A native hook call with `COPILOT_AGENT_JOB_ID` or `COPILOT_AGENT_CALLBACK_URL` in its environment is a cloud agent call. It exits 0 and does nothing else, unless the config has `copilotCloud: true`; then it runs as a local native call. An inherited hook call (ADR-0015) with one of these markers does not give the `SessionStart` notice, unless the config has `copilotCloud: true`. `SessionStart` and `agentStop` first probe a write to `<cacheRoot>/repos/<hash>/state` and remove the empty dirs that the probe made. When the write fails, `SessionStart` gives `additionalContext` and each `agentStop` gives a progress line, both `mutagate inactive: cannot write <path>`; `postToolUse` takes the silent exception path. mutagate does not start a worker, block, write a marker file or write outside the sandbox there.
`install --agent copilot` writes one file: `.github/hooks/mutagate.json` for the project scope, and `$COPILOT_HOME/hooks/mutagate.json`, else `~/.copilot/hooks/mutagate.json`, for the user scope. It never writes a `settings.json`. The file has the form `{"version":1,"hooks":{…}}` with one entry for each of `sessionStart`, `preToolUse` (matcher `create|edit|str_replace_editor|apply_patch`), `postToolUse` (the same matcher plus `bash|powershell|read_bash`, ADR-0019), `subagentStart` (ADR-0020) and `agentStop` (`timeoutSec` 600, ADR-0018). The other entries have `timeoutSec` 30. Each entry gives the internal event and `--harness copilot`. `sessionStart` also gives the install stamp (ADR-0017). No entry has `command`. On macOS and Linux, `bash` has the wrapper command of ADR-0013 and ends with ` || true # mutagate`, and `powershell` is `exit 0 # mutagate`. Only an install on Windows writes a real `powershell` command: `& '<node>' '<runtime>' hook <Event> --harness copilot; exit 0`. `install` stops with exit 2 and names the file when the other scope has a mutagate Copilot file. `doctor` gives a warning when Copilot runs more than one file with mutagate hooks: the two scopes, or another file in a hooks dir. `uninstall --agent copilot` removes the mutagate entries and deletes the file when no other entry stays, and then an empty `.github/hooks/`. `--agent auto` selects Copilot when the environment has `COPILOT_CLI` or `COPILOT_AGENT_SESSION_ID`, or the repo has `.github/hooks/` or `.github/copilot/`; with `--scope user`, also on `COPILOT_HOME` or `~/.copilot`. `.github/workflows`, `.agents/skills` and `copilot-instructions.md` do not select it. A `.claude/` dir that has only `skills/` does not select Claude when one of these signals is present. When these signals select Copilot and a Claude project install has no Copilot file, `doctor` gives a warning. `doctor` also gives a warning when the skill copy that Copilot loads (`.github/skills`, else `.agents/skills`, else `.claude/skills`) and the copy that the hooks run have a different `VERSION` (#35 D26). The README claims the Copilot CLI only. It names the VS Code Copilot harness only after a passing record `test/evidence/vscode/copilot-<os>.json`, made again for each release.
Rationale: Local payloads use other output and exit codes, and Copilot is the supported VS Code harness (#35 D21). A cloud job gates a repo whose owners did not choose mutagate for the cloud agent (#35 D22). In a sandbox, the failed cache root is the only state root, so no state can last (#35 D23). The probe removes its dirs, so a repo that mutagate does not use gets no data dir, as with the other harnesses. An exit code other than 0 from `preToolUse` denies each edit, and the `sh` form fails under PowerShell (#35 D24). With two scopes, Copilot runs both files for each event, the user file first, with the same payload (spike S9): each hook does its work two times, each `agentStop` runs the gate two times, and one block reason is lost (#35 D5, spike S8). A workflow or a skill dir does not show that the team uses Copilot, and an install arms each teammate and the cloud agent (#35 D25). Copilot runs the Claude hooks too, but mutagate keeps those calls inert (ADR-0015). Two copies with a different `VERSION` give the hooks and the CLI calls of the agent different fingerprints. VS Code needs its own evidence (#35 D28).
Alternatives: Run the cloud agent by default. The committed file reaches every cloud job, so teams that did not choose it get the gate. Rejected. Keep a marker file or a state root outside the sandbox. That is a sandbox escape. Rejected. Write the hooks into a Copilot `settings.json`. One entry with an error there makes Copilot reject all hooks of the file. Rejected. Accept both scopes. Rejected for the reason above.
Consequences: Spike S16 confirmed the cloud markers: the cloud hook environment has them, and no local CLI hook or agent shell environment has them. That environment also holds `COPILOT_SDK_AUTH_TOKEN` and `GITHUB_VERIFICATION_TOKEN`. The cloud agent sends `toolArgs` as JSON text, and mutagate reads it as the object of a local call. For `apply_patch` it sends the raw patch with absolute paths in the headers, and mutagate keeps these paths. A repo that opts in with `copilotCloud: true` gives the cloud job the mutagate gate. In a Copilot sandbox, mutagate is inactive and says so at each `agentStop`. A project file made on macOS or Linux does nothing on Windows. A user who wants the user scope must first uninstall the project scope, and the reverse. A second file made by hand costs one more handler and a second, fast gate pass. A blocking `agentStop` hook of another tool that runs after the mutagate hook replaces the mutagate reason and uses its one block.
