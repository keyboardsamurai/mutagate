# ADR-0016: Detection and target resolution use the Git file list
Status: accepted 2026-11-07
Concern: Detection and target resolution walked the full repo, at SessionStart and at each test edit. The walk read directories that Git ignores. It also listed the files in them, so a generated or ignored file could become a target. On large repos this work made hooks slow.
Decision: In a Git repo, the repo file list for detection and target resolution comes from `git ls-files -co --exclude-standard`: tracked files, and untracked files that Git does not ignore. mutagate then removes the names that the repo walk removes (README, State). It also removes deleted tracked files, tracked symlinks, submodules and nested repositories. When `git` fails, when the repo is not in a Git repo, or when Git lists no file, mutagate walks the repo as before. Fingerprint inputs and the Python and C# copies continue to use the walk.
Rationale: The ignore rules are the project's statement of what is not source. Git does not read ignored directories. A build can need ignored generated sources, so fingerprints and copies must keep them.
Alternatives: A persistent file list that directory mtimes invalidate; it is complex and can go stale. A faster walk; it still reads ignored directories and still lists ignored files. Both rejected.
Consequences: Detection does not count a file that Git ignores, and that file is not a target. To make it a target, track it (`git add -f`) or change the ignore rule. A test that Git ignores still registers when the agent edits it or names it in `mutagate run`. Files in a submodule or a nested repository are not targets of the outer repo. An untracked symlink is listed, because Git does not mark it. A repo inside a directory that an outer repo ignores (for example a home directory under Git that ignores `*`) is walked.
Related: ADR-0013 (a portable install also needs `git` and fails in a submodule or nested repo)
