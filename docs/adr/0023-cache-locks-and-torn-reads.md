# ADR-0023: Cache locks and torn reads
Status: accepted 2026-11-10
Concern: Hook calls, workers, the cache prune and the CLI share one data dir. A hook timeout kills a process, and a crash can stop a write half way. Both leave a lock file or a half-written JSON file behind.
Decision: Every lock (session state, target, tool install, JVM compile, .NET project) is one file that `lock` opens with `wx`, mode 0o600, with the pid and a random token. The holder touches the file every 10 s. A lock is abandoned (`abandoned`; `inFlight` uses it) when its mtime is over 60 s old or its pid is dead (`kill 0` fails with a code other than EPERM). One waiter removes an abandoned lock under `<lock>.break`. It removes the lock of a live pid only after it saw the mtime unchanged for 15 s of monotonic time, or half its budget when that is shorter (2.5 s for the state lock), and only while the lock still holds the token it saw. Timers do not count system sleep, so after a wake a live holder touches the file up to 10 s late. Release deletes the file only while it holds its own token. A waiter polls after 1, 2, 4, 8 and 16 ms, then every 25 ms, and gets no lock when its budget ends. The budgets: the state lock `<data>/state/<session>.json.lock` 5 s (`updateState` throws `session state busy`); the target lock `<data>/locks/<key>.lock` the run budget; the tool install lock `<root>/tools/<name>@<ver>.lock` (under the cache root, not the data dir), the JVM compile lock `<data>/locks/jvm-compile.lock` and the .NET project locks `<data>/locks/dotnet-<hash>.lock` (one per `.csproj`) the time to the run deadline; the prune 0. `atomic` writes a temp file and renames it, with no fsync. State, result and classpath files are read through `cacheJson`: JSON that does not parse reads as missing. A torn result makes the target pending, so it runs again. Torn state starts blank, with one stderr note (none under a quiet profile). The cache root is a real path, so tools get no symlinked alias of the data dir. `runTarget` takes the stat keys (size, mtime, ctime, inode) of every file that `fingerprint` hashes before the first fingerprint of an attempt and again after the second. It publishes the result only when the generation, the fingerprint and the stat keys did not change. A run that saw a write publishes nothing, also when the write restored the bytes.
Rationale: The heartbeat and the pid tell a dead holder from a slow one. The token stops a release or a break from deleting the lock of a newer holder. An fsync on each write costs each hook call; a rerun or a blank state costs less than a wrong read. Equal bytes at the start and at the end do not show what the runner read between them: an edit and its undo during the run gave a result of other bytes as current (verify-stop-gate F1).
Alternatives: An advisory lock. Rejected: Node has no built-in one, it is not portable, and a waiter cannot see the holder. An fsync on each write. Rejected: hook latency.
Consequences: Other hooks wait at most 5 s for the state lock, so compute `fingerprint` and the stat keys before `updateState`. A run that saw a write runs again once, then the target stays pending. A filesystem whose timestamps are too coarse to see an edit and its undo, or a tool that restores mtime and ctime, can still give a result of other bytes. A holder that does not touch its lock for 15 s of a waiter's monotonic time loses it; its release then deletes nothing.
