# ADR-0019: Copilot outbox delivery
Status: accepted 2026-11-09
Concern: Copilot has no async hooks and no hook that wakes the agent. A `postToolUse` hook must end fast, but a mutation run takes minutes. Copilot adds the top-level `additionalContext` of a `postToolUse` hook to the tool result, and the model reads it. A `-p` session can end with no more tool calls. The bash tool puts a command in the background after `initial_wait` (default 30 s), and the end of that command comes through `read_bash`. A detached child process continues after the hook exits, after the hook timeout kill and after `copilot -p` exits. Evidence: Copilot CLI 1.0.107, spikes S6, S8 and S13 (#35).
Decision: A new native `postToolUse` write event with session targets or a test path starts one spawned handler: a detached `hook PostToolUse --mutate --harness copilot` process with the raw payload on stdin. A second delivery of the same event (the same edit token) starts no handler. The spawned handler runs the async branch: it waits for 6 s quiet and for repo builds (`gateWaitSec` or less), yields to a newer handler and runs the stale targets again. It writes no output. It puts the report of each run into the session outbox, one entry `{key, run, text}` for each target, from its newest run. `run` is the `started_at` of the run. A pass removes the entry of the target. Each pass that a run records resets `reported`, also a pass from `check`, an `agentStop` or a worker. A delivery point is a `postToolUse` call of the root agent (no `agentId`) for `create`, `edit`, `str_replace_editor`, `apply_patch`, `bash`, `powershell` or `read_bash`, also when the call names no file. A delivery point removes the entries from the outbox. It sends the entries whose run gives the current result of the target (`loadResult` finds a result with the `started_at` of the entry) and whose text is not the `reported` text of the target, as one top-level `additionalContext` of 1,800 characters or less, and sets `reported` to their text. It does not send the other entries. mutagate reads the results before it takes the state lock. An entry that a handler adds after that read stays for the next delivery point. A subagent call registers targets and starts a spawned handler, but it is not a delivery point. When `check` shows a below or error result, or `agentStop` blocks with a result, the gate sets `reported` and removes the entry of that target from the outbox. `check` also removes the entry of each target whose result it shows, for example an unscored result. `run --sync` does the same for a target that has an entry. An `agentStop` that allows keeps the entries: the model does not see its progress lines (ADR-0018), so the next delivery point sends them. An `agentStop` while a spawned handler waits for quiet runs the target inline (ADR-0018). The target lock and the fresh result then stop a second run by the handler. A background infrastructure error goes out as `additionalContext`, never as a block. An agent-caused error blocks once at `agentStop` (ADR-0002).
Rationale: The spawned handler uses the tested async code of Claude Code and Codex. The gate at `agentStop` stays the decision (ADR-0018), because a `-p` session can end with no more tool calls. The outbox only gives the reports earlier. With `bash` and `read_bash` as delivery points, a report gets to the agent while it runs its tests or `check`. The gate and the async hook of Claude Code use the same `reported` value, so a report does not go out twice: not at two delivery points, and not after a block or a `check` with the same report. A pass resets `reported`, so a later regression goes out again. A stale entry tells about a test or code that the agent changed after the run.
Alternatives: An entry with the generation of its run, sent when the target has a fresh result of that generation. Rejected: `check`, `run --sync` or an `agentStop` run can replace the result in the same generation, for example after a shell edit, and then an old report goes out after a pass. Reports only at `agentStop`. Rejected: a detached handler continues (S6), so the agent can get the reports while it works. Set `reported` when the handler adds the entry. Rejected: the agent does not see the entry before a delivery point. A marker that makes `agentStop` wait for a handler that waits for quiet (#35 D16). Not necessary: the gate runs the target inline, and the target lock keeps one run. Calculate the fingerprint at a delivery point only when a write event came after the entry. Rejected: a shell command can change a file with no write event, and then a stale report goes out.
Consequences: A report waits for the next write or shell call of the root agent. When the session ends before that call, only the gate decision gets to the agent. A delivery point with entries calculates the fingerprint of each target. This time increases with the module of the target: about 40 ms in a small repo and about 470 ms in a module of 15,000 files. The 80 ms hook bound applies to the small repo; the performance test reports the large figure (`copilot_drain_unbudgeted`) and does not limit it. A digest cache keyed by file stat and shared between processes can make this time shorter (a follow-up issue, not 0.9.2). The spawned handler has no hook timeout. It stops at the rerun deadline (850 s). `postToolUseFailure` is not a delivery point.
